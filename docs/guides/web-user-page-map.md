## 2. 侧边栏实际结构（实测）

侧边栏分两组。**「系统设置」组默认是收起的**，采集默认状态下只能看到组标题
「系统设置」，展开后才出现 6 个子项（这是真实现状，写文档时容易漏）：

```text
业务导航
├── 工作台        /console/home
├── 新建任务      /console/planning
├── 我的任务      /console/tasks
├── 数据资产      /console/results
├── 质量评估      /console/evaluation
├── 数据清洗      /console/cleaning
└── 账户与帮助    /console/help

系统设置（仅管理员可见；默认收起）      ← 实测：默认只显示组标题
├── 运营监控      /console/operations
├── AI 服务       /console/admin/providers
├── 结果存储      /console/admin/storage
├── 生成规则      /console/admin/strategies
├── 生成指令      /console/admin/prompts
└── 操作记录      /console/admin/audit
```

### 2.1 阶段页的侧边栏高亮归属

阶段页不在侧边栏，靠 `stageRouteNavMap` 把当前路径映射到一个侧边栏项做高亮。
该映射**从阶段工作台声明派生**（`App.tsx:132-134`，由 #79 引入，消除了三处漂移）：

```text
/console/domains   → /console/tasks    （我的任务）
/console/questions → /console/results  （数据资产）
/console/reasoning → /console/results  （数据资产）
/console/rewards   → /console/results  （数据资产）
/console/exports   → /console/results  （数据资产）
```

> **设计观察**：同一条流程的 5 个阶段被分到**两个不同的高亮父项**，
> 用户从第 1 步走到第 2 步时侧边栏高亮会跳一次。

## 3. 任务详情页（唯一枢纽）

实测：任务详情页 `/console/tasks/{id}` 是 5 个阶段页的**唯一入口**。

### 3.1 实测的阶段卡片跳转目标

采集脚本逐个点击 5 张卡片，记录实际落点（`test/artifacts/page-structure/hub-and-form.json`）：

| 卡片 | 实测跳转目标 |
| --- | --- |
| 第 1 步：主题结构 | `/console/domains` |
| 第 2 步：问题生成 | `/console/questions` |
| 第 3 步：答案内容 | `/console/reasoning` |
| 第 4 步：质量评估 | `/console/rewards` |
| 第 5 步：导出交付 | `/console/exports` |

### 3.2 主按钮（随状态变化）

任务详情页顶部主按钮的文案与目标由 `statusToActionRoute()` 决定：

| 任务状态 | 主按钮文案 | 跳转目标 |
| --- | --- | --- |
| `draft` | 先确认主题结构，再启动问题生成 | `/console/domains` |
| `domains_confirmed` / `questions_*` | 启动问题生成，补齐任务素材 | `/console/questions` |
| `reasoning_*` | 启动答案生成，形成可评审内容 | `/console/reasoning` |
| `rewards_*` | 启动质量评分，准备交付结论 | `/console/rewards` |
| `export_*` | 导出结果包并通知验收 | `/console/exports` |

### 3.3 枢纽页的其它区块（实测可见控件）

除 5 张阶段卡片与主按钮外，还实测到：

- 「进阶能力」面板（由本轮 #65/R10 新增）：L2 长链标准步骤 / L3 难度分层统计 /
  L4 GRPO 提示词 / L5 SFT 记录 / L6 导出格式与字段映射 / R1 方向生成 / R1 评估裁判，
  每项带「执行 + 刷新」两个按钮；
- 「质量与交付」区多个「查看」按钮，指向对应的阶段页；
- 刷新状态 / 恢复指引按钮。

> **该面板是 issue #90 成文之后新增的**（#90 基于 `53aa5db`，而 R10 在之后合并）。
> 因此 #90 原文的「5 张卡片 + 质量与交付」之外，任务详情页现在还承担
> **7 项进阶能力的入口**，枢纽作用进一步加重。

## 4. 空状态文案（实测原文）

阶段页在「未选中任务 / 尚无产物」时给出的文案，逐条采集自真实渲染：

| 路由 | 实测空状态文案 |
| --- | --- |
| `/console/planning` | 尚未生成估算 · 填写参数后点击「估算规模」。 |
| `/console/domains` | 尚未生成方向结构 · 先创建任务，再生成方向结构。 |
| `/console/questions` | 尚未生成题目 · 请先确认主题，再开始生成题目。 |
| `/console/reasoning` | 尚未生成答案 · 请先完成题目生成，再开始生成答案。 |
| `/console/rewards` | 尚未生成质量评估 · 先完成答案生成，再触发质量评估。 |
| `/console/exports` | 尚未生成导出结果 · 完成质量评估后，即可触发导出。 |
| `/console/cleaning` | 这个任务还没有清洗过。在上面「发起一次清洗」里选择阶段与规则，点「开始清洗」。 |

> （「先确认主题」「先完成题目生成」…），且与流水线顺序一致。
> 这是本系统做得好的地方，值得在改造时保留。

## 5. 完整操作流程（实测）

### 5.1 主流程：登录 → 产出数据

```text
[1] 登录
     └→ /console/tasks（我的任务）

[2] 创建任务
     侧边栏「新建任务」 → /console/planning
     填写：任务名称（可选）/ 任务主题 / 目标样本数
           （管理员额外可见：领域数 n / 每领域方向数 m / 每方向问题数 x /
             生成策略 / AI 服务 / 存储配置 —— 实测共 9 个可见字段）
     可点「估算规模」预览
     点「创建任务」 → 自动进入 /console/tasks/{id}

[3] 第 1 步 主题结构     /console/tasks/{id} → 卡片1 → /console/domains
     「生成方向结构」→「批量确认」→「确认结构」
     ★ 必须点「返回当前任务」回详情

[4] 第 2 步 问题生成     卡片2 → /console/questions → 「开始生成题目」→ ★ 返回详情
[5] 第 3 步 答案内容     卡片3 → /console/reasoning → 「开始生成答案」→ ★ 返回详情
[6] 第 4 步 质量评分     卡片4 → /console/rewards   → 「开始质量评估」→ ★ 返回详情
[7] 第 5 步 导出交付     卡片5 → /console/exports   → 「开始导出结果」→ 下载
```

**5 次「返回详情 → 点卡片 → 点生成」的往返**，根源是 §1.2 实测的「阶段页无向前导航」。
量化分析见 [`web-user-ux-review.md`](./web-user-ux-review.md)。

### 5.2 支线：质量评估（多模型互评）

```text
/console/evaluation（侧边栏「质量评估」）
├── 维度管理    → 导入内置维度（实测库中 58 条）/ 新建自定义维度 / 编辑 / 停用
├── 新建评估    → 选数据集 → 抽样模式（全量/按比例/按条数）→ 选维度 → 选裁判 → 创建并启动
├── 运行列表    → 历史运行
└── 结果与报告  → 打分明细与汇总
```

### 5.3 支线：数据清洗

```text
/console/cleaning（侧边栏「数据清洗」）
├── 流程步骤条（5 步，可点击跳转）
├── 发起一次清洗 → 选任务 + 勾选阶段（问题/思维链/答案）+ 启用规则 → 开始清洗
├── 清洗记录     → 历史运行 + 查看报告
├── 关键词库     → 新增 / 导入 / 启用停用
└── 清洗规则     → 新建规则（名称/优先级/最少命中数/动作/生效阶段）
```

### 5.4 管理员配置

```text
AI 服务     → 名称 / 协议 / 基础 URL / 模型 / 并发 / 超时 / 密钥 → 获取模型列表 / 连通性测试
结果存储    → 名称 / 提供方 / 端点 / 地域 / 存储桶 / AK / SK / Path Style
生成规则    → 名称 / 规划模式 / 领域数 / 每领域问题数 / 答案变体 / 奖励变体
生成指令    → 名称 / 阶段 / 版本 / 系统指令 / 用户指令
操作记录    → 只读审计列表（实测无操作按钮）
```

## 6. 发现的设计问题（逐条附实测证据）

### 6.1 🔴 同名不同页：「质量评估」

| 入口 | 路由 | 实测页面标题 | 实际功能 |
| --- | --- | --- | --- |
| 侧边栏「质量评估」 | `/console/evaluation` | **质量评估** | 人工配置的多模型互评（维度管理 / 新建评估 / 运行列表 / 报告） |
| 任务详情「第 4 步：质量评估」 | `/console/rewards` | **质量评分结果中心** | 流水线内的自动评分阶段 |

**实测确认**：侧边栏项文案是「质量评估」，阶段 4 的卡片文案也是「第 4 步：质量评估」，
而两者落到的页面标题分别是「质量评估」与「质量评分结果中心」。
用户从名字无法区分何时该用哪个。

### 6.2 🔴 三处导航对同一流程阶段的指向互不相同（实测）

同一套「5 步流程」，三个入口给出三种目标：

| 阶段 | 侧边栏 | 任务详情卡片 | 数据清洗流程条（`CleaningFlowSteps.tsx:22-26`） |
| --- | --- | --- | --- |
| 生成数据 | 无 | `/console/domains`…`/console/rewards` | `/console/tasks` |
| 质量评估 | `/console/evaluation` | `/console/rewards` | `/console/evaluation` |
| 导出交付 | 无（在「数据资产」内） | `/console/exports` | `/console/results` |

实测来源：清洗页可见按钮含「前往质量评估」「前往导出交付」，其 `onNavigate` 目标
由 `CleaningFlowSteps` 的 `route` 字段给出，即 `/console/evaluation` 与 `/console/results`；
而任务详情页对应卡片实测落到 `/console/rewards` 与 `/console/exports`。

### 6.3 🔴 阶段页无「下一步」（往返的根源）

见 §1.2 的逐页实测：5 个阶段页共 18 个可见按钮，
**向前的导航数量为 0**。

对比：数据清洗页**做了**阶段间导航（「前往质量评估」「前往导出交付」等 4 个按钮）。
同一个产品里两种做法并存 —— 说明「阶段间导航」在本仓库已有实现范式，可直接复用。

### 6.4 🟠 阶段页不在侧边栏，且高亮归属分叉

见 §2.1。5 个阶段页无侧边栏入口，高亮归属被分到两个不同父项。

### 6.5 🟠 任务详情页是单点枢纽，且职责持续膨胀

所有阶段入口都从 `/console/tasks/{id}` 发散，且必须回到它才能去下一阶段。
本轮又在同一页加了「进阶能力」面板（7 项能力 × 2 按钮）。
该页一旦不可达，整条流水线瘫痪 —— 这正是 issue #61 的破坏力来源（已修复）。

### 6.6 🟠 新建任务页字段数已增至 9 个

实测（`test/artifacts/page-structure/hub-and-form.json`）管理员可见字段标签：

```text
任务名称（可选） / 任务主题 / 目标样本数（条） /
领域数 n / 每领域方向数 m / 每方向问题数 x /
生成策略 / AI 服务 / 存储配置
```

`#90` 成文时是 6 个字段，本轮 #85（n/m/x 用户可控）又加了 3 个。
页面自身说明仍写着「只填任务主题和目标规模即可」——**文案与界面继续背离**，
且新增的 3 个字段是**产品需求要求用户可控**的（`功能说明.txt` 步骤 1/3），
不能简单删掉，更应做渐进披露分组。

### 6.7 🟠 管理员配置混入普通创建流程

「生成策略 / AI 服务 / 存储配置」与业务必填项同屏平铺。
实测后果已在 issue #83 记录：**存储未配置会导致答案阶段必然失败**，
而用户在创建任务时看不出这一点。

### 6.8 🟡 运营监控入口默认收起

「系统设置」组默认收起，管理员需要先展开才能看到运维入口。
对既有管理员而言这是额外一次点击；对新管理员则是「找不到入口」。
（这同时解释了本轮 `test/l15_browser_human_e2e.mjs` 早期误报 —— 它没有先展开就去找子项。）

## 7. 建议的页面设计规范

### 7.1 导航体系收敛为「一套主流程 + 独立工具页」

```text
主流程（任务详情驱动，5 步；每步提供「下一步」）
  任务详情 /console/tasks/:id
    ├── 第 1 步 主题结构 → 下一步：生成问题
    ├── 第 2 步 问题生成 → 下一步：生成答案
    ├── 第 3 步 答案内容 → 下一步：质量评分
    ├── 第 4 步 质量评分 → 下一步：导出交付
    └── 第 5 步 导出交付 → 完成，查看数据资产

独立工具页（侧边栏；与单任务流程解耦）
  工作台 / 新建任务 / 我的任务 / 数据资产
  多模型互评 / 数据清洗 / 账户与帮助
```

### 7.2 消除同名冲突（术语规范）

| 现状 | 建议 |
| --- | --- |
| 侧边栏「质量评估」= `/console/evaluation` | 改名 **「多模型互评」**（与其 caption「多模型互评与打分」一致） |
| 阶段「第 4 步：质量评估」= `/console/rewards` | 保留「质量评分」，不再与上者共用「评估」 |
| 「领域 / 方向 / 一级方向 / 主题结构 / 方向结构」混用 | 建立统一术语表（`功能说明.txt` 的原文用词是 n 个「领域」与 m 个「方向」） |

### 7.3 每个阶段页提供「下一步」

在阶段页 PageHeader 的按钮区补一个向前的按钮：

```text
[返回当前任务] [刷新] [下一步：{下一阶段名} →]
```

`statusToActionRoute()` 已有完整映射，可直接复用；`CleaningFlowSteps` 提供了
**同仓库的实现范式**（步骤定义 = `{key, label, detail, route}` 数组 + onNavigate 回调）。

### 7.4 统一阶段跳转目标

以**任务详情页的 5 个阶段页**为唯一权威，让侧边栏、数据清洗流程条、
数据资产页的跳转全部指向同一批路由，消除 §6.2 的「三处不同」。

### 7.5 页面职责边界

| 页面类型 | 职责 | 不应包含 |
| --- | --- | --- |
| 任务详情 | 展示流程进度、作为阶段枢纽 | 具体阶段操作（应跳转到阶段页） |
| 阶段页 | 完成本阶段操作 + 提供下一步 | 其它阶段的操作 |
| 工具页（互评 / 清洗） | 独立于单任务的分析与治理 | 流水线阶段推进 |
| 数据资产 | 跨任务的产物检索与下载 | 阶段推进 |

### 7.6 新建任务页渐进披露

- 默认只显示 **任务名称 / 任务主题 / 目标样本数**；
- **n / m / x** 归入「生成参数（可选）」：它们是需求要求的用户可控项，
  但「留空用默认值」已经实现（R13 已把 0 定义为「未设置」），因此可折叠而不丢能力；
- **生成策略 / AI 服务 / 存储配置**归入「高级设置」，仅管理员可见且默认折叠；
- 页面文案改为与界面一致（不再说「只填主题和规模即可」）。

### 7.7 保留既有优点

以下做法在本轮采集中确认有效，改造时应保留：

1. **阶段页空状态写明前置条件**（「请先完成题目生成」）；
2. **失败态的恢复入口**（`trustSignal` 的 `nextStep` 会给出「回到某阶段」按钮）；
3. **`stageRouteNavMap` 从声明派生**（#79 引入），消除三处漂移 —— 同样的手法
   可用于 7.4 的「统一跳转目标」。
