# 评估与清洗使用说明

面向使用者的中文操作手册。不需要了解数据库、队列、模型这些内部概念，按下面的步骤走就能完成「创建任务 → 生成数据 → 评估质量 → 清洗异常 → 导出结果」。

> **实现状态提示**：本文档中的「数据清洗」相关页面已可用（后端 L11/L12 已合并）。「质量评估」页面的完整交互界面由 L13 交付、后端评估运行由 L9/L10 交付，在本文写作时仍**待合并**；凡涉及这些页面的具体交互，本文按已冻结的接口契约描述，并标注「待 L13/L14 合并」。后端接口本身可以先用 `curl` 直接调用（见第 7 节）。

## 1. 完整操作路径一览

```
登录 → 新建任务 → 等待生成（n 领域 / m 方向 / 长链标准 / x 问题）
     → 分支：GRPO 数据集 → 生成教师评判提示词
             SFT 数据集  → 生成思维链 + 答案
     → 质量评估：选维度 → 配抽样 → 选裁判 → 看报告
     → 数据清洗：配关键词 → 发起清洗 → 看报告
     → 导出：选格式 → 下载
```

左侧一级导航（`apps/web-user/src/App.tsx`）中与本流程相关的是：

| 导航 | 路径 | 用途 |
|---|---|---|
| 新建任务 | `/console/planning` | 创建数据集任务，设定 n / m / x 与训练类型 |
| 我的任务 | `/console/tasks` | 查看生成进度 |
| 数据资产 | `/console/results` | 查看结果与导出文件 |
| 质量评估 | `/console/evaluation` | 多模型互评与打分（待 L13 合并） |
| 数据清洗 | `/console/cleaning` | 拒答与异常拦截 |
| 导出交付 | `/console/exports` | 查看导出与交付 |

## 2. 从建任务到拿数据（分步骤）

### 第 1 步：登录

打开系统地址（本地开发是 `http://127.0.0.1:3210`），用管理员账号登录：

- 邮箱 `admin@company.com`
- 密码 `admin123456`

登录成功后浏览器会拿到一个会话 Cookie（`llm_session`），后续所有请求都靠它鉴权。如果页面提示「登录状态已失效」，重新登录即可。

### 第 2 步：新建任务

进入 **新建任务**（`/console/planning`）。这一页你要给出的是：

| 你要填的 | 含义 | 建议 |
|---|---|---|
| 根关键词 | 数据主题，例如「军事」 | 越具体越好，太宽会导致下游领域发散 |
| 领域数量 n | 由关键词生成多少个领域 | 例如 5 |
| 方向数量 m | 每个领域再展开多少个方向 | 例如 5；最终得到 n×m 条方向 |
| 每方向问题数 x | 每个方向生成多少个具体问题 | 例如 2；最终得到 n×m×x 个问题 |
| 训练类型 | GRPO 或 SFT | GRPO 生成教师评判提示词；SFT 生成思维链 + 答案 |
| 生成模型 | 用哪个模型生成数据 | **记住这个选择**，评估时它会被自动排除出自评 |
| 存储位置 | 结果存哪里 | 用默认即可 |

n、m、x 都持久化在库里：n 存在生成策略的 `generation_strategies.domain_count`（即任务估算里的 `estimate.domainCount`），m 存 `datasets.direction_count`，x 存 `datasets.questions_per_direction`。任务创建后仍可调整 m / x 再重新入队。

### 第 3 步：等待生成

点「开始生成」后，你会看到一条「已入队」的提示，然后任务进入队列。

**「已入队」不等于「立刻开始」**：真正的生成在后台 worker 里跑，调用大模型一次可能耗时 30~120 秒。你可以在 **我的任务** 里看进度，进度来自 `generation_runs` 表（阶段 / 状态 / 已完成单元数 / 总单元数）。

生成顺序是固定的（每一步依赖上一步的产物）：

1. **n 个领域 + m 个方向**（阶段 `directions`）
2. **每个方向的长链思维标准步骤**（阶段 `chain-standards`）
3. **每个方向 x 个具体问题**（阶段 `questions`），带难度分层与自动去重
4. **分支**：GRPO → 教师评判提示词（阶段 `grpo`）；SFT → 思维链 + 答案（阶段 `sft`）

**中途失败怎么办**：任务卡片上会出现「继续」按钮，点它就是从上次断点续跑（后端按 `generation_runs.cursor` 记录进度），不会把已经生成好的部分重做一遍。

### 第 4 步：确认长链标准步骤（可选，但强烈建议）

每个方向生成出来的长链思维标准步骤是可以人工改的。它是后面 SFT 思维链的「对标模板」，改对了能明显提升数据一致性。

- 查看：**我的任务** → 选数据集 → 长链标准
- 编辑：改步骤的标题/描述/检查点，写一句修改说明，保存
- 每次保存都会新增一个版本，历史版本随时可查、可回溯

### 第 5 步：拿到结果

- SFT 数据集：每条形如「问题 → 思维链 → 答案」，思维链会标注与长链标准的对齐情况。
- GRPO 数据集：每个问题一份教师模型评判提示词，覆盖你设定的每个打分档次。
- 在 **数据资产** 页可以预览、筛选，然后在 **导出交付** 页选格式下载（JSONL / CSV / Parquet / Alpaca / ShareGPT）。

## 3. 评估模块怎么用

入口：左侧导航 **质量评估**（`/console/evaluation`）。页面由四个页签组成：维度、新建评估、运行、报告。

> 交互细节以 L13 合并后的实现为准；下面的每一步都对应一个已冻结的后端接口，因此逻辑是确定的。

### 3.1 第一步：确认评估维度

**在哪点**：质量评估 → 维度 页签。

**会看到什么**：按分类分组的维度列表。系统内置 **58 个**长链思考维度，分 7 类：

| 分类 | 数量 | 关注什么 |
|---|---|---|
| 长链推理 `long_chain` | 12 | 步数够不够、步骤衔接、有没有自我纠错、分支论证 |
| 忠实性 `faithfulness` | 9 | 有没有幻觉、引用可不可追溯、数值单位对不对 |
| 指令遵循 `instruction` | 7 | 是否遵守约束、格式是否合规、边界与歧义处理 |
| 领域贴合 `domain_fit` | 8 | 术语、场景、法规、资源约束是否贴合具体领域 |
| 答案质量 `answer_quality` | 8 | 结论明确、可执行、有风险提示与备选方案 |
| 稳健性 `robustness` | 8 | 抗诱导、拒答处理、安全合规、偏见控制 |
| 效率 `efficiency` | 6 | Token 效率、思考密度、无套话填充、适时收敛 |

所有维度都是 1~5 分制，每个维度都带一句判据说明（鼠标悬停或展开可见）。

**要不要新增维度**：如果内置维度覆盖不到你的业务（例如某个行业专有的合规口径），可以新增自定义维度，写清名称、分类、描述和判据。自定义维度和内置维度在评估时同等使用。

**下一步去哪**：如果维度列表是空的，先点「初始化内置维度」（幂等操作，重复点不会产生重复数据），然后进入新建评估。

### 3.2 第二步：新建评估

**在哪点**：质量评估 → 新建评估 页签。

**要选的四项**：

| 项 | 怎么选 |
|---|---|
| 被评估数据集 | 选一个已经生成好数据的数据集 |
| 评估维度 | 默认全选；只想看某几类时按分类筛选。**建议首次评估先选 10~20 个维度**，全选 58 个会显著拉长耗时 |
| 抽样方式 | 全量 / 按比例 / 按数量，见下 |
| 裁判模型 | 至少选 1 个；建议选 2~3 个不同来源的模型 |

**抽样方式怎么选**：

| 方式 | 含义 | 什么时候用 |
|---|---|---|
| 全量 | 逐条评估数据集里所有数据 | 数据量小（几百条以内）、要做最终交付验收 |
| 按比例 | 按百分比抽样，例如 10% | 数据量大，想快速看整体水平 |
| 按数量 | 抽固定条数，例如 200 条 | 想控制成本与耗时，同时保证样本量固定 |

**抽样是确定性的**：同一次评估重跑，抽到的样本完全一样。这样两次报告的差异一定来自数据本身或模型，而不是「这次运气不好抽到了别的样本」。

**下一步去哪**：保存后进入「运行」页签。

### 3.3 第三步：选裁判模型（关键步骤）

**在哪点**：运行页签 → 裁判设置。

**会看到什么**：系统列出所有可用的模型，每个模型后面标注状态：

- 可用
- 已排除：生成者模型，禁止自评
- 已排除：与生成者同源（相同 BaseURL + Model），禁止自评
- 已排除：模型未启用
- 已排除：模型未配置 API Key

**为什么生成数据的模型不能当裁判**：用自己的模型评自己生成的数据，分数会系统性偏高——它偏好自己的措辞和推理风格，评出来的高分只说明「自洽」，不说明数据好。系统会自动识别并排除，**连换了名字、id 不同但实际是同一个模型的注册项也会被识别出来**（按 base_url + model 判定同源）。

**下一步去哪**：确认裁判列表后，点「开始评估」。

### 3.4 第四步：等评估跑完

点「开始评估」后同样只是「已入队」。评估在后台逐条 × 逐裁判 × 逐维度调用模型打分，耗时大致与「样本数 × 裁判数 × 维度数」成正比。运行页签会显示进度（已打分条数 / 总条数），以及每个裁判各自的进度和错误信息。

**如果某个裁判中途失败**：其他裁判的结果不会丢，这次评估会被标记为「部分失败」，报告里会说明哪个裁判失败了、失败原因是什么。

### 3.5 第五步：怎么看懂报告

报告页签给出四层信息：

**① 整体分**：这个数据集被所有裁判打出的综合分（按维度权重加权）。

**② 各裁判分数**：每个裁判给的整体分。**如果几个裁判的分数差得很多，说明模型之间分歧大**，这本身就是一个重要信号——见下面的「裁判一致性」。

**③ 各维度分数**：哪个维度强、哪个维度弱。这是最有行动价值的一层，例如：

- `lc_step_sufficiency`（推理步数充分性）低 → 生成时应该提高长链标准的步骤数要求
- `fa_hallucination_control`（幻觉控制）低 → 需要在提示词里强调「不确定就说不确定」
- `aq_actionability`（可执行性）低 → 答案偏理论，应要求给出具体动作与责任人

**④ 最弱条目**：分数最低的若干条数据，直接点进去看是哪条、哪个裁判给了低分、理由是什么（每个分数都带 `rationale`）。这批数据是最值得优先清洗或重生成的。

**裁判一致性怎么读（重点）**：

- 一致性**高** → 各模型判断接近，结论可信度高。
- 一致性**低** → 各模型判断分歧大。**这不代表数据一定差，而是代表「这次评估的结论可信度有限」**。常见原因：
  - 维度本身主观性强（例如「表达精炼度」「场景贴合度」），不同模型的审美不同；
  - 数据的质量处在「好与不好的边界上」，模型各自踩在不同一侧；
  - 某个裁判的模型能力明显弱于其他裁判，拉低了共识。
- **一致性显示为「不适用」** → 说明当前只有 1 个有效裁判（或某维度上只有 1 个裁判给了分）。此时**不存在「裁判间差异」这个概念**，系统会明确标注「不适用」，而不是显示一个 0。**如果这里显示 0，请把它理解为「无法计算」，不要理解成「完全不一致」**。

**一致性低时怎么办**：① 增加裁判数量（2~3 个不同来源的模型）；② 对低分且分歧大的条目做人工复核；③ 如果某个维度长期一致性很低，考虑把它从评估维度里去掉，避免它污染整体分。

## 4. 清洗模块怎么用

入口：左侧导航 **数据清洗**（`/console/cleaning`）。页面分三块：关键词库、规则、清洗运行与报告。

### 4.1 第一步：了解内置关键词

**在哪点**：数据清洗 → 关键词库。

**会看到什么**：系统内置 **41 条**关键词，分 5 类：

| 分类 | 严重度 | 条数 | 示例 |
|---|---|---|---|
| 中文拒答 `refusal` | block（拦截） | 13 | 对不起、我不能、我无法提供、作为一个AI |
| 安全话术 `safety` | block（拦截） | 8 | 违反、涉及敏感、违法违规、使用政策 |
| 英文拒答 `english_refusal` | block（拦截） | 10 | I cannot、I'm sorry、As an AI、violates policy |
| 不确定回避 `uncertainty_evasion` | warn（告警） | 5 | 请咨询专业人士、无法保证准确性 |
| 占位符 `placeholder` | warn（告警） | 5 | TODO、待补充、此处省略、N/A、连续省略号 |

严重度的含义：

- `block`（拦截）：命中就按规则处置（标记或剔除）。
- `warn`（告警）：只记录命中，不影响数据可用性。**这类内容不一定有害**，例如「请咨询专业人士」在医疗、法律类问题里可能是恰当的回答，所以默认只告警。

匹配模式有三种：`contains`（包含，37 条）、`prefix`（前缀，3 条）、`regex`（正则，1 条）。

### 4.2 第二步：加自己的关键词

**在哪点**：关键词库 → 新增 / 批量导入。

**单个新增**要填：匹配内容、分类、匹配模式、严重度、备注。

**批量导入**：一次贴入多行关键词，选好分类和严重度即可。

**两个注意点**：

1. **内置关键词只能停用，不能删除**。如果你删，系统会提示「内置关键词不可删除，请改为停用」。这是刻意的：内置库是清洗的基线，允许删除会导致一次误删让清洗静默失效（匹配不到任何东西 → 报告显示 0 命中 → 你以为数据很干净）。
2. **同一分类下重复的模式会被跳过**，导入结果里会显示 `inserted`（实际新增）与 `skipped`（已存在被跳过），不会报错。

**下一步去哪**：配好关键词后，去规则页签。

### 4.3 第三步：配清洗规则

**在哪点**：数据清洗 → 规则。

规则决定「命中之后做什么」，字段含义：

| 字段 | 含义 | 怎么配 |
|---|---|---|
| 规则名称 | 唯一标识 | 例如「问题阶段严格拦截」 |
| 生效阶段 `stageScope` | 这条规则管哪些阶段 | 可选 `question`（问题）/ `reasoning`（思维链）/ `answer`（答案），可多选 |
| 命中阈值 `minHits` | 命中几次才触发 | 默认 1；调高可以只拦「反复出现」的样本，减少误伤 |
| 动作 `action` | 命中后怎么处理 | `drop` 剔除 / `flag` 标记待复核 / `retry` 重新生成 |
| 优先级 `priority` | 多条规则同时命中时的先后 | 数字小的优先 |
| 启用 | 是否生效 | 停用即可保留配置不生效 |

**默认建议**：不做配置时，清洗按内置规则执行（三阶段全扫，命中即按严重度处置）。**建议先跑一次默认清洗看看报告，再决定要不要加规则**——一上来就配一堆 `drop` 很容易误删。

### 4.4 第四步：发起清洗

**在哪点**：数据清洗 → 清洗运行 → 发起清洗。

**要选什么**：清洗阶段（默认三个阶段全选）。建议第一次三个都选，看完整报告。

点「开始清洗」后同样是「已入队」，后台 worker 会：

1. 取出数据集里每条数据的问题、思维链、答案文本；
2. 按你启用的关键词逐条匹配；
3. 把命中写进明细，并按规则决定动作；
4. 回写每条数据的清洗状态：`clean`（干净）/ `flagged`（待复核）/ `dropped`（已剔除）；
5. 生成清洗报告。

**重复点会怎样**：如果这个数据集已经有一次清洗在排队或运行中，系统会直接复用那一次并提示「清洗任务已在队列中」，不会并发清洗两次。

### 4.5 第五步：怎么看懂清洗报告

报告给四层信息：

**① 总体数字**：扫描了多少条、命中多少条、剔除多少条。

**② 分阶段统计**：问题 / 思维链 / 答案三个阶段各自的扫描数、命中数、剔除数和命中率。

> **为什么分阶段看很重要**：三个阶段的污染模式完全不同。问题阶段命中通常意味着这条数据从源头就废了；思维链阶段命中说明推理过程断裂；答案阶段命中有时只是免责声明，数据本身还能用。所以**不要只看总体命中率，要看是哪个阶段在命中**。如果只有答案阶段命中率高，很可能是你的关键词过宽，把正常的免责声明也算了进去。

**③ Top 关键词**：命中最多的关键词及示例片段。这里是调优的主要线索：

- 如果某条关键词命中了大量样本，点开看片段，判断是不是误伤；
- 如果 `warn` 类关键词命中很多，通常说明生成提示词里需要补一句「不要用这类回避话术」。

**④ 结论**：系统根据统计给出的文字结论（例如「问题阶段命中率偏高，建议检查生成提示词」）。

**还能看什么**：命中明细可以按阶段筛选，每条明细带：数据 ID、阶段、命中的关键词、命中文本、上下文片段、处置动作。

**下一步去哪**：被 `drop` 的数据不会进入后续导出；被 `flag` 的可以在数据资产里人工复核后决定保留或删除；`clean` 的数据可以放心导出。

## 5. 常见问题排查

每个问题都按「现象 → 原因 → 处理」写。

### 5.1 任务入队了但一直没反应

**现象**：点了「开始生成」/「开始清洗」/「开始评估」，页面显示「已入队」，但进度一直不动。

**原因**：任务只是被放进了一个 Redis 队列，真正干活的是 worker 进程。以下任一情况都会导致「没人取任务」：

1. worker 进程没在运行；
2. worker 消费的队列名和 API 入队用的队列名不一致；
3. worker 起来了但消费的是另一个环境的队列（多个环境共用同一个 Redis 时最常发生）；
4. 任务其实被**去重机制**抑制了——同一个数据集在 10 分钟内重复入队同一个阶段时，系统会直接返回「已在队列中」而不再真正入队。

**处理**：

1. 先确认提示文字。如果消息是「已在队列中」而不是「已入队」，说明命中了去重，**等 10 分钟**再点一次，或换一个数据集试。
2. 确认 worker 在运行，且 API 与 worker 的队列名一致（同一套配置里 `WORKER_QUEUE_NAME` 必须两边相同）。
3. 看 worker 日志有没有收到任务；没有收到就是队列名不一致。
4. 以上都正常但仍不动，查看任务的错误信息（`generation_runs.error_summary`）——很可能是模型调用失败（见 5.2）。

### 5.2 任务失败，错误信息里提到模型

**现象**：任务状态变成失败，错误信息里出现模型相关的报错。

**原因**：大模型调用失败。常见是三类：模型服务地址不可达、API Key 无效或未配置、单次调用超时（推理型模型一次响应可能需要 30~120 秒，超时设置太短会被中断）。

**处理**：到「AI 服务」管理页确认模型的地址与 API Key 配置正确，并用页面的「测试」功能验证连通性。修好后回到任务点「继续」从断点续跑，已生成的部分不会重做。

### 5.3 评估分数异常高

**现象**：报告里整体分接近满分，但你自己看数据明显没那么好。

**原因**：最常见的就是**生成数据的模型被当成了裁判**（自评导致分数虚高）。其次是维度选得太少或太容易（例如只选了格式类维度）。

**处理**：

1. 到评估运行页的裁判列表，检查每个裁判的状态。被排除的会标注原因（「生成者模型，禁止自评」/「与生成者同源」）。**如果列表里出现了一个没有被标注排除、但其实就是同一个模型的裁判，请检查它的 base_url + model 是否与生成模型一致**——系统按这两个字段判定同源，只要有一项被改过就会被判为不同源。
2. 确认裁判数量 ≥ 2，且来自不同模型。
3. 检查维度选择：只选 `instruction` / `efficiency` 这类容易拿高分的维度，会让整体分虚高。建议至少包含 `long_chain` 与 `faithfulness` 两类。

### 5.4 裁判一致性很低

**现象**：报告里裁判一致性很低，或者各裁判分数差距很大。

**原因**：不同模型对同一条数据的判断分歧大。这不是系统故障，而是一个真实信号：**这次评估的结论可信度受限**。常见诱因是维度本身主观性强、数据处在质量边界上、或某个裁判模型能力明显弱于其他裁判。

**处理**：

1. 增加裁判数量，选 2~3 个能力相近但来源不同的模型。
2. 看「最弱条目」里分歧最大的那几条，人工复核一次，判断哪一方的判断更合理。
3. 如果某个维度长期一致性很低，考虑从评估维度里去掉它，避免它拉低整体结论的可信度。
4. **注意区分「一致性 = 0」与「一致性 = 不适用」**：只有 1 个有效裁判（或某维度只有 1 个裁判给分）时，系统会标注「不适用」；如果你看到的是 0，那是真实的不一致，不是计算不出来。

### 5.5 清洗把正常数据拦了

**现象**：清洗报告显示大量命中，但点开片段发现这些数据其实没问题。

**原因**：关键词过宽。典型例子：

- 用 `contains` 匹配了「我不能」，但数据里是「我不能确定该方案是否可行，需要进一步验证」——这是合理的不确定性表达，不是拒答；
- 用 `warn` 级别的「请咨询专业人士」匹配了医疗、法律类问题的正常结尾；
- 匹配模式选错了：本想精确匹配短语却用了 `regex`，或反过来。

**处理**（按影响从小到大）：

1. **把严重度从 `block` 降为 `warn`**。数据不再被剔除，只记录命中，你可以先观察一段时间。
2. **收紧匹配**：把 `contains` 改成更精确的 `prefix`（只匹配开头），或改写 `regex` 提高精确度；也可以把过宽的短词删掉，换成更完整的短语。
3. **调高规则的 `minHits`**：从 1 调到 2 或 3，只拦「反复出现」的样本，减少单次误伤。
4. **改规则动作为 `flag` 而不是 `drop`**：先标记、人工复核，确认后再决定剔除。
5. **停用误伤的关键词**（内置关键词不能删除，但可以停用）。
6. 改完关键词或规则后，**重新发起一次清洗**（同一个数据集重新跑会生成新的清洗运行记录，历史报告不会被覆盖，可以对比）。

### 5.6 导出里数据比预期少

**现象**：导出的条数少于数据集里的条数。

**原因**：清洗时被判定为 `drop` 的数据不会进入导出；另外导出可能应用了筛选条件。

**处理**：到清洗报告里看被剔除的条数与原因，确认这些剔除是你想要的；如果剔错了，按 5.5 调整后重新清洗，再重新导出。

## 6. 术语速查

| 中文 | 英文/原名 | 含义 |
|---|---|---|
| 领域 | domain | 根关键词下属的第一层分类，例如「军事」下的「海军」 |
| 方向 | direction | 领域下属的第二层细分，例如「海军」下的「海上巡逻」 |
| 长链思维标准步骤 | chain standard | 某个方向应有的推理步骤模板，可人工编辑、带版本 |
| 裁判 | judge | 参与评估打分的模型 |
| 维度 | dimension | 评估的一个考察点，1~5 分制 |
| 抽样 | sampling | 从数据集中选取一部分进行评估，支持全量/比例/数量 |
| 剔除自评 | exclude self-evaluation | 禁止生成数据的模型担任该数据集的裁判 |
| 裁判一致性 | judge consistency | 不同裁判对同一数据判断的一致程度 |
| 清洗阶段 | cleaning stage | 问题 / 思维链 / 答案三处分别扫描 |
| 严重度 | severity | `block` 拦截 / `warn` 仅告警 |
| 命中明细 | finding | 一次清洗中某条数据在某阶段命中了某关键词的记录 |
| 清洗状态 | cleaning status | `clean` 干净 / `flagged` 待复核 / `dropped` 已剔除 |
| 入队 | enqueue | 把任务放进后台队列，等待 worker 执行 |

## 7. 附：不通过界面时怎么验证

界面尚未合并的模块（评估运行 / 评估报告）可以直接用接口验证。登录拿到 Cookie 后：

```bash
# 登录，保存 Cookie
curl -s -c /tmp/cookies.txt -X POST http://127.0.0.1:3210/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@company.com","password":"admin123456"}'

# 查看可用的裁判模型（注意 excluded / excludeReason 字段）
curl -s -b /tmp/cookies.txt http://127.0.0.1:3210/api/v1/admin/eval/judges

# 查看评估维度分类
curl -s -b /tmp/cookies.txt http://127.0.0.1:3210/api/v1/eval/dimensions/categories

# 初始化内置维度（幂等）
curl -s -b /tmp/cookies.txt -X POST http://127.0.0.1:3210/api/v1/eval/dimensions/seed

# 查看清洗关键词库
curl -s -b /tmp/cookies.txt 'http://127.0.0.1:3210/api/v1/cleaning/keywords?active=true'

# 查看某个清洗运行的报告
curl -s -b /tmp/cookies.txt http://127.0.0.1:3210/api/v1/cleaning/runs/1/report
```

接口的完整清单与请求/响应格式见 `docs/plans/eval-and-cleaning-plan.md` 第 3 节；架构背景见 `docs/architecture/phase-8-eval-and-cleaning.md`。
