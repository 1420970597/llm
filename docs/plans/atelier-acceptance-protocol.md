# Atelier 真实用户任务验收方案（T34 交付物）

> 本文件是 Issue [#160](https://github.com/1420970597/llm/issues/160) 的任务 **T34**
> 的交付物之一。T34 的原文要求：邀请 **5–8 名真实数据研发使用者**完成交付目标、
> 两版试制比较、扩量、异常恢复、证据审阅、发布下载，并记录首次点击、迷路/回退、
> 无法解释的阻塞、需要帮助次数与任务结果，分别验证 owner/reviewer/viewer 的旅程，
> 且用 SFT 与 GRPO 项目而不是只测预置演示数据。
>
> **当前状态：真实用户研究尚未执行。** 本文件是**可执行的验收方案**与**证据清单**，
> 不是执行记录。因此 T34 对应的验收项与 DoD 条目在真实会话完成之前**不得勾选**。
> 这一点在 [`../todo.md`](../../todo.md) 与
> [`atelier-implementation.md`](atelier-implementation.md) §1.1 中同样如实标注。

## 1. 参与者

| 维度 | 要求 |
|---|---|
| 人数 | 5–8 人（少于 5 人无法区分「个人习惯」与「产品问题」） |
| 背景 | 真实数据研发使用者：写过 SFT/偏好数据的同学、数据标注负责人、训练工程师 |
| 角色覆盖 | 至少 1 名 owner、1 名 reviewer、1 名 viewer（三角色旅程不同，见第 3 节） |
| 排除 | 本仓库的开发者（他们知道实现细节，无法代表「第一次用」） |
| 环境 | 一个真实可用的部署（不是本地 docker-compose 的单人环境），有真实 provider 连接与结果存储 |

**不得**用模拟用户或未发生的访谈填充本节。若只安排了 3 人，就写 3 人并说明
为什么少于 5 人（例如「只有 3 名符合条件的使用者可安排」）。

## 2. 任务脚本（每位参与者都要走完）

按顺序执行，**不提示下一步该点哪里**（提示会掩盖「首次点击」这类证据）。
卡住超过 3 分钟才允许给一次最小提示，并记录为 1 次「需要帮助」。

| # | 任务 | 观察点 | 通过判据 |
|---|---|---|---|
| 1 | 创建一个 SFT 项目：目标、n/m/x、试制规模、门槛、预算 | 是否需要理解 provider/storage/strategy 等内部概念 | 全程不出现「不知道这个字段是什么」的阻断 |
| 2 | 设计：蓝图各节点、覆盖矩阵、思维标准 | 是否能在不看文档的情况下完成；非法配比是否被拦住并指出字段 | 保存成功且能解释每个节点的作用 |
| 3 | 两个 pilot 独立试制 + 同基准比较 | 是否理解「比较的是同一批输入下的两个方案」 | 报告显示配对完成数、缺失样本与风险；无「显著性」断言 |
| 4 | 扩量（scale） | 是否理解「改配置要新建批次」 | 新批次与 pilot 有独立 ID，快照固定 |
| 5 | 异常恢复：暂停 / 恢复失败项 | 是否理解「暂停=停止新请求，在途仍会完成并计费」 | 界面同时显示两条信息；恢复不重跑成功项 |
| 6 | 质量实验 + 审阅：分派、判断、冲突协调、规则证据 | 是否理解「缺分≠0 分」「证据版本变化需重新判断」 | 报告的分母/覆盖可解释；相反意见保留为 conflict |
| 7 | 发布：候选 → 门槛阻塞 → 冻结 → 下载 | 阻塞是否可定位到具体对象；下载文件名/版本是否可理解 | 发布后修改项目不改变旧下载的字节 |
| 8 | 用 GRPO 项目重复 1–7 的关键路径 | 界面是否按目标类型切换节点/字段/发布 schema | GRPO JSONL 逐行可解码且档位与判据一一对应 |
| 9 | （reviewer）只读审阅与判断 | 写控件是否被服务端拒绝而不仅是界面隐藏 | 直接调用写 API 被拒 |
| 10 | （viewer）只读 + 下载已发布 | 是否有不该看到的运维/成本信息 | 只能读取被授权内容与已发布文件 |

## 3. 三角色旅程

| 角色 | 可做 | 不可做（必须被服务端拒绝） |
|---|---|---|
| owner | 设计、运行、判断、发布、管理成员 | —— |
| reviewer | 读取、提交人工判断 | 设计/运行/发布 |
| viewer | 读取被授权内容、下载已发布文件 | 判断、发布、任何写入 |

每个角色的**越权尝试**必须直接调 API 验证（界面隐藏控件不算证据）。

## 4. 记录表（每位参与者一份）

| 字段 | 记录方式 |
|---|---|
| 首次点击 | 每个任务的第一步点在哪里（是否与设计意图一致） |
| 迷路/回退 | 次数与具体位置（例如「在发布页找了 2 分钟映射版本」） |
| 无法解释的阻塞 | 原话引用 + 当时的界面状态（截图或 URL） |
| 需要帮助次数 | 每次的记录与提示内容 |
| 任务结果 | 完成 / 部分完成 / 未完成 + 原因 |
| 耗时 | 每个任务的时间（用于发现「最慢的一步」） |
| 原话 | 至少 3 条直接引用（不要转述） |

## 6. 阻塞级问题的处置

真实会话中发现的问题按下表分级；**阻塞级**必须在 T34 关闭之前修掉并留下回归测试。

| 级别 | 定义 | 处置 |
|---|---|---|
| 阻塞 | 任务无法完成，或产出会被误判为可信（例如缺分被显示成 0 分） | 立即修复 + 补回归测试；重跑该参与者的该任务 |
| 严重 | 能完成但需要帮助，或完成结果与预期不同 | 排期修复，并在本文件记录处置 |
| 提示 | 文案/布局/效率问题 | 记入后续迭代，不阻塞 T34 |

## 7. 收尾条件

T34 可以关闭当且仅当：

1. 5–8 名真实参与者完成第 2 节的任务，记录表与证据齐备（或如实写明未达标及原因）；
2. 第 5 节中「待人工」的条目全部转为「已收集」或明确降级为产品缺口；
3. 阻塞级问题全部修复并带回归测试；
4. [`../../todo.md`](../../todo.md) 与本文件、`atelier-implementation.md` §1.1 的状态**三者一致**；
5. 总 Issue #160 才可关闭 —— 且**不因为 M4 已可演示就标记整个改革完成**。
