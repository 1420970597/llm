# 产品调研：重新建立训练数据工厂的信息架构

调研日期：2026-09-20。源码基线：`f2fed44`。本次交付为设计方案与独立交互原型；未替换线上业务前端。

## 1. 问题定义与调研方法

用户提出的核心问题是：一个菜单进入后承担多个互不相关的任务，缺少独立详情页和明确的跳转设计。成功标准不是菜单改名、增加卡片或把长页面改成更多页签，而是让用户知道“我在处理哪个对象、当前页面做什么、动作后去哪、失败怎么恢复”。

本次采用四类证据，并区分其证明范围：

| 方法 | 实际完成的工作 | 能证明什么 / 不能证明什么 |
|---|---|---|
| 业务需求审读 | 阅读本地《功能说明.txt》、README、todo、阶段架构文档 | 证明训练数据生产的业务范围；原始需求文件按仓库规则不提交 |
| 代码与契约审查 | 阅读 App.tsx、评估/清洗视图、API 客户端、Go 路由与对象模型 | 证明页面结构、上下文存储及接口存在性；不把“有接口”等同于所有边界均正确 |
| 当前界面走查 | 从当前源码运行 `npm run build -w apps/web-user`，独立静态容器 :18421 连接既有 review API，用 Chromium 登录并查看任务、评估、清洗 | 证明当前界面入口和页面组织；不启动真实生成，不修改既有业务记录；观察环境不是用户访谈 |
| 外部桌面调研 | 实际获取下表官方页面，核对正文与可借鉴模式 | 证明公开产品文档中的模式；没有声称完整使用过竞品，也没有虚构用户访谈或可用性统计 |

既有 #84 / #90 是历史证据，不作为当前事实的替代。`todo.md` 的勾选完成项也不等于当前体验已达标。本次先核对源码，再采集界面。

## 2. 业务定位：专业训练数据制备，不是泛内容生成器

原始需求要求：关键词 → n 个领域 → 每领域 m 个方向 → 每方向思维标准 → 每方向 x 个问题 → SFT 或 GRPO 产物 → 多格式导出；另有独立多模型互评和阶段清洗。

`todo.md` 里“让普通用户不理解模型、奖励数据”等简化方向与原始业务存在张力。最终选择是：保留 SFT、GRPO、领域、方向、标准、裁判这些对决策必要的术语；把存储密钥、并发参数、公共配置维护移到专门页面。不能为了看起来简单而隐藏 n/m/x 或把 GRPO 错做成“答案评分”。

### 用户角色与需要完成的工作（待实访验证的角色假设）

| 角色 | 工作目标 | 高价值决策 | 主要页面 |
|---|---|---|---|
| 数据生产人员 | 为指定训练阶段交付足量、可用数据 | 训练类型、领域覆盖、规模、产物是否齐备 | 生产任务、数据集、导出 |
| 数据质量人员 | 找到弱点、解释分歧、处理误报 | 评估范围、维度、裁判、样本保留或隔离 | 质量评估、数据清洗、样本详情 |
| 平台管理员 | 保证模型与存储可用，维护公共资源 | 连接、默认配置、指令变更与影响 | 资源库、系统管理 |

这些是工作角色，不是本次凭空引入的三套权限。现有身份仍是普通用户与管理员；第一阶段按现有服务端能力控制访问。资源维护的细粒度权限属于后续能力。

## 3. 当前界面与代码发现

| ID | 当前证据 | 用户代价 | 设计处置 |
|---|---|---|---|
| F01 | `EvaluationView.tsx` 默认 `tabKey='dimensions'`；4 个页签共用 `/console/evaluation` | 想看评估结果却先进入维度管理；报告不能单独收藏 | 默认评估运行列表；新建、详情、逐条评分、报告分开路由 |
| F02 | 同文件 `selectedRunId` / `tabKey` 存在 React state，刷新重新初始化 | 在报告中刷新会丢失所选运行上下文 | `/evaluations/:runId/report` 直接从地址恢复 |
| F03 | `CleaningView.tsx` 同时加载关键词、规则、运行、报告，并将其排在同页 | 清洗操作与全局配置互相干扰 | 清洗只管理运行和报告；规则、关键词进入资源库 |
| F04 | 当前 Chromium 采集清洗页标题含“发起一次清洗、清洗记录、关键词库、批量导入、清洗规则、清洗之后去哪里” | 一个入口承担配置、执行、分析、全局维护 | 为不同对象和动作分别设计页面，不用折叠面板掩盖职责混乱 |
| F05 | `App.tsx` 任务详情在阶段卡片之后继续渲染“进阶能力” | 思维标准、GRPO、SFT 等核心能力变成杂项 | 标准、问题集、训练产物成为任务的可定位子页面 |
| F06 | `App.tsx` 的 `renderRecordPage` 按钮为返回、刷新和本阶段生成；下一步主要是文字建议 | 用户完成阶段后要重新寻找入口 | 同一任务内提供路由化的阶段导航和下一步入口 |
| F07 | 部分链接用 `stageRouteWithTask(...)?taskId=`，但一些主动作仍直接调用 `navigate(statusToActionRoute(...))`；状态集中在 `activeDatasetId` | 同种跳转对上下文的处理不统一 | 所有对象地址都显式带 ID；统一由路由解析对象，禁止全局“选中任务”决定写入对象 |
| F08 | “质量评估”同时用于 rewards 阶段与独立 eval 运行 | 生成奖励记录、GRPO 教师提示词、多模型互评容易混淆 | 三者分开命名、分开对象和页面 |
| F09 | `App.tsx` 4,386 行，路由、数据、各类表单、弹窗和阶段操作集中 | 页面边界弱导致反复增加面板；导航修改易漂移 | 后续按业务模块拆分；集中路由字典，单页单一主要目标 |
| F10 | 当前页面仍显示部分 key、接口分类等内部字段；清洗与评估的默认视图偏配置 | 用户在判断数据质量前先理解实现 | 名称、质量含义、范围优先；标识留在详情中的可复制技术信息 |
| F11 | 原任务卡使用“5 步”线性主流程，SFT、GRPO 与标准被归入额外能力 | 流程叙事不等于真实业务依赖 | 按训练目标显示分支，标准是核心步骤 |

## 5. 关键产品决策与备选方案

| 决策 | 采用的方案 | 放弃的方案及原因 |
|---|---|---|
| 信息架构 | 对象为主，任务内按流程定位 | 全部按流水线阶段做一级菜单：跨任务检索弱；所有能力藏在任务详情：职责再次膨胀 |
| 数据集与任务 | 数据集承载内容与交付，任务承载执行与恢复；第一阶段共用 dataset ID，第二阶段解耦任务记录 | 直接假装已有独立 task API：会把未实现能力包装成现成能力 |
| 评估入口 | 运行列表为默认页，配置维度进入资源库 | 维度管理作为默认页：高频“看结果”被低频维护占据 |
| 详情 vs 抽屉 | 完整样本、运行、报告用页面；简短确认/只读预览用弹窗 | 所有编辑放抽屉：长链文本、版本比较和复杂表单空间不足 |
| 生产分支 | SFT / GRPO 明确分流，标准与问题是共同前置 | 为了沿用旧 5 步流程把 SFT / GRPO 继续叫“进阶” |
| 清洗处置 | 默认标记复查，支持隔离并保留原始内容 | 关键词命中后直接认为样本不可用：易误伤引用与否定语境 |
| 自动执行 | 目标形态是结构确认后按依赖执行；第一阶段提供真实可用的阶段跳转 | 只在浏览器连续调用接口模拟后台编排：用户离开页面会中断 |
| 导航数量 | 6 个稳定业务入口 + 管理入口 + 独立帮助/账户 | 追求固定“5 个菜单”：菜单数本身无法保证职责清晰 |

## 6. 尚未被证明的假设与后续验证

1. 用户能区分“数据集”与“生产任务”。用真实任务进行树测试：给出“找内容”与“处理超时”两类目标，看首次点击是否正确。
2. 大多数用户需要连续执行，少数需要逐步复核。上线前记录真实偏好，默认值可以改变，但后台执行必须可恢复。
3. 全局质量人员是否需要跨数据集复查队列，需要访谈确认。第一版先保留数据集/运行范围，不直接新增一个万能“质量中心”。
4. 生产规模、并发、费用模型尚无可靠统计。不得设计虚构 ETA、金额或“百分百高质量”。
5. 团队人数、日常数据规模、训练框架分布未获得用户实证。本方案提供可验证的设计假设和访谈提纲，不伪称调研了不存在的用户。

建议下一轮 5–8 名实际使用者覆盖生产、质量、运维工作，完成 7 个验收任务；指标与完整步骤见 [04-delivery-and-validation.md](04-delivery-and-validation.md)。
