### 必须避免的契约误判

1. `StageEnqueueResult` 目前含 datasetId/stage/state/message/acceptedAt，不含 runId。设计中的精确运行跳转需要返回 ID 或可验证的查询定位机制。
2. `validateExportPrerequisites` 当前对 SFT 采用“存在一条 generated 且思维链或答案非空即可”的条件；非 SFT 回退要求 rewards 覆盖问题。它**不等同于**“所有所选 SFT 样本字段齐备”，也不等同于完整的 GRPO 教师提示词校验。设计实施必须按训练类型、映射与所选范围统一校验，不能在 UI 画绿勾就视为满足。
3. 当前 `Filters` 是 map，worker 只识别有限字段。传入一个任意 sampleIds 或 status 并不自动实现已选导出。
4. `GenerationRun` 的计量单位随阶段变化；方向运行使用方向数，标准使用方向/标准数，问题和产物使用自己的单位。只显示当前阶段可靠进度，不能用固定状态百分比覆盖事实。
5. 现有 `EvalItem` 有 payload 快照，但不能据此推断所有资源版本、裁判权重和样本集合引用都已不可变。
6. 清洗 `drop / flag / retry` 的当前语义需结合 worker/store 实现验证。新 UI 的“隔离可撤销”是新契约，不是对旧 `drop` 的文案替换。
7. `GET export/formats` 会幂等补种映射。调研只读操作避开不必要的该接口调用；实现时应明确读取副作用并逐步改进。

### 1.2 评估统计契约（目标 v2，服务端计算）

原型图表中的数字是示例。生产报告需要服务端提供 `aggregationVersion`、量表/权重快照和各指标分母；旧报告保留旧算法标签，不在前端偷偷重算为新的含义。

令样本为 i，裁判为 j，维度为 d，原分数为 s，量表下限 L、上限 U，权重 w>0。

1. **合法分数**：状态成功、L≤s≤U、U>L，才是有效评分单元。超范围、解析失败或缺失均记缺分，不截断成合法值，也不当作 0。
2. **量表归一化**：`z(i,j,d)=(s-L)/(U-L)`，范围 0–1。用于统一展示时 `display=1+4*z`；原始量表和值始终可在证据页读取。
3. **样本×裁判得分**：仅当该裁判所有选定维度都有有效分时，`J(i,j)=Σ(w_d*z(i,j,d))/Σw_d`。缺一个必需维度即无完整 J，不自动重分配权重造成更高分。
4. **样本得分**：仅当所有选定独立裁判都有完整 J 时，`I(i)=ΣJ(i,j)/裁判数`。裁判等权；如将来允许裁判权重，必须版本化并在报告展示。
5. **总体得分**：对有完整 I 的样本取等权平均，展示为 1–5 分。分母为完整评分样本数，不是目标样本数。未完成运行即使存在部分 I，也只显示“临时结果”，不出最终结论。
6. **覆盖**：抽样覆盖率=`本次快照样本数/可评数据集样本数`；评分完成率=`有效评分单元/(样本数×裁判数×维度数)`；完整样本率=`有完整 I 的样本数/本次样本数`。重试覆盖原单元，不重复增加分子。
7. **维度图**：按有效单元均值显示，但每维度必须显示有效/应有单元数；不能把维度均值再平均冒充总体得分。
8. **低分**：默认完整样本显示分 `<3/5`；未完整评分不归入低分，进入“待完成”。阈值可在配置冻结后读取，报告必须显示。
9. **分歧**：同一样本至少两个完整裁判得分，`max(display J)-min(display J)≥1.0` 标记明显分歧；同时说明参与裁判数和是否缺评，不把分歧自动等同于错误。

缺分算例：两个维度，权重 2:1；维度一 1–5 分、维度二 0–10 分。裁判 A 得 4、8，则 z 为 0.75、0.8，J=0.7667，显示 4.07/5。裁判 B 得 3、缺失，则 B 无完整 J；该样本没有最终 I。有效单元 3/4，完整样本 0/1；不能显示“该样本最终 4.07 分”。

现有 `evalReport/evalScores` 提供报告与明细，但以上版本化量表、完整性和聚合口径需要核验/补充服务端契约。不得把本设计公式描述为当前后端已实现算法。

### 1.3 GRPO 下游能力边界

当前 `targetKind` 字段存在，但 `eval_store_items.go` 的样本加载主要读取问题、SFT 和 legacy reasoning。不能凭请求中写入 `grpo` 就认为教师提示词与奖励档位已被评估。GRPO 评估应增补 payload（question、framework、judgePrompt、levels、rubrics）、适用维度和结果说明；接好前界面保留 GRPO 上下文并禁用启动。

清洗已知阶段为 question / reasoning / answer。GRPO 可以先清洗 question；teacherPrompt / rubric 不伪装成 answer，专用清洗适配后才显示可选。原型 GRPO 清洗报告明确“教师提示词未扫描”，不宣称全产物质量通过。

## 2. 分期实施与出口标准

工期不是凭空承诺；以下是依赖顺序与可独立验收的工作包，排期需结合实际人力确定。

| 阶段 | 工作包 | 出口标准 | 是否依赖新后端 |
|---|---|---|---|
| P0 设计 | 本次调研、IA、64 页原型、控件规范、状态矩阵、验收脚本 | 设计可独立阅读，关键链路可点，依赖标明，图文可远程查看 | 否 |
| P1a 壳与路由 | layout、route registry、breadcrumbs、列表/详情壳、旧链接兼容 | 深链接/刷新/浏览器前后退可用；没有全局 activeDataset 写入歧义 | 主要否 |
| P1b 高频拆页 | 评估默认列表；新建、run、scores、report；清洗列表/创建/报告；关键词/规则拆出 | 每页一个主任务，点击有明确落点，现有功能一个不丢 | 主要否；列表规模有限时需标注 |
| P1c 生产与资产 | SFT/GRPO 创建、标准编辑、问题与产物、样本详情、运行恢复、历史评分入口 | 原有生产和导出能力走通；逐阶段下一步可用；不伪装自动执行 | 部分组合 |
| P2 数据契约 | 独立任务/产物快照、readiness、失败记录、分页、清洗预览/复查、选中导出 | 接口先有测试，再接按钮；无法落地的能力不展示成可用 | 是 |
| P3 连续执行 | 持久编排、通知、恢复与规模验证 | 用户离开和 worker 重启后流程仍可继续，错误有持久证据 | 是 |

P1 可以先解决用户现在指出的页面堆叠和跳转混乱，不应把页面拆分拖到“大一统新任务系统”全部完成之后。P2/P3 功能只有后端可验证后才开放为真实操作。

建议前端模块：`app/routes`、`app/layout`、`features/datasets`、`production`、`evaluation`、`cleaning`、`resources`、`admin`，共享 `ListPage`、`ObjectHeader`、`RunStatus`、`EmptyState`、`ErrorPanel`、`ResourceForm`。共享组件负责一致性，业务页面保留明确职责，不再回到一份巨型 App.tsx。

## 4. 度量与验收任务

以下是**设计验收目标，不是已经测得的用户研究结论**。

| 任务 | 起点 → 终点 | 成功条件 | 建议目标 |
|---|---|---|---|
| U1 创建 SFT | 工作台 → 结构待确认 | 正确填写主题、n/m/x，理解总量 | 参与者≥80%无辅助完成；不以填写时间代替理解 |
| U2 创建 GRPO | 新建 → 产物配置 | 找到奖励档位，知道交付物不是答案评分 | ≥80%正确解释 SFT/GRPO 分支 |
| U3 找评估报告 | 评估列表 → 指定报告 → 刷新 | 仍是同 runId，能看抽样范围 | 入口到指定报告≤2次页面选择；刷新不丢上下文 |
| U4 维护关键词 | 清洗列表 → 关键词详情 | 找到资源入口，不误启动清洗 | 首次点击正确率≥80%，全程无意外业务写入 |
| U5 处理误报 | 命中列表 → 上下文 → 保留 | 理解关键词只是疑似命中，留下理由 | 回列表后位置与筛选保留，计数更新 |
| U6 失败恢复 | 工作台 → 失败运行 → 续跑 | 知道只处理失败范围，成功数据保留 | 不重建整任务，不重复入队 |
| U7 下载交付 | 数据集 → 导出记录 → 下载 | 确認文件范围与格式，成功拿到数据 | 已有文件入口≤2次页面选择；文件与配置一致 |

统一路径计数方法：一次点击链接/菜单/主按钮算一次页面或决策动作；输入字符、等待时间、滚动不混在“点击数”里。对现状和新方案使用同一组任务、同一数据、同一口径，不发布不具可比性的“减少 80%”数字。

### 产品与工程必须共同通过的验收

- 64 页目录及新增/编辑模式无死路、无自重定向，404/403有明确信息。
- URL包含对象 ID；跨任务跳转、刷新、新标签、前后退不读写错对象。
- SFT与GRPO流程、字段及导出前置不同，历史 reasoning/rewards 数据仍可访问。
- 评估默认运行列表，报告可直达；切换裁判/维度不会把分母算错。
- 生成者及同源模型不能自评，前后端使用同一候选判定。
- 清洗预览不修改样本，处置可追溯，关键词误报能复查。
- 筛选导出与已选导出范围可复现，按真实 targetKind 与映射检查完整性。
- 存储变更不破坏旧文件，下载以 artifact 原始位置为准。
- 运行中离页不停止任务；重复点击、断网重试不产生重复工作。
- 表单空值、非法范围、并发编辑冲突均有可执行错误；不静默清空草稿。
- 1440、1024、390 宽度布局可用；表格局部滚动；键盘焦点不被固定区遮住。

## 5. 后续用户研究提纲

每位参与者先用自己的语言描述最近一次数据制备目标，再做 U1–U7 的角色适用子集。访谈者不解释菜单含义，只记录首次点击、回退、卡住的位置和对结果的理解。最后询问：

1. 找内容与处理运行失败时，你分别会进入哪里？
2. 你如何判断 SFT/GRPO 产物已可训练？最需要看到哪三项证据？
3. 哪些阶段必须手动复核，哪些可以自动继续？
4. 什么情况下你会改 n/m/x，是否需要精确成本预估？
5. 多个裁判意见冲突时，你需要哪些上下文才能行动？
6. 清洗规则误判一次后，你希望如何恢复和避免再发生？
7. 团队如何命名任务、复用模板、交付文件、复现实验？

保留原话、任务结果和观测记录，区分参与者意见与研究者推断。没有实际参与者之前，上面的比例只是验收目标。
