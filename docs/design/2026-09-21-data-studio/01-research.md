# 从公开 Web UI 研究到新的产品结构

研究日期：2026-09-21。任务是重新设计理想产品，不以既有菜单、数据库表或接口为设计边界。上一版调研中的业务需求作为输入；界面、导航、交互模型重新选择。

## 方法和证据层级

本轮实际用 HTTP 获取公开页面，再用 Chromium 查看 SaaSFrame 分类与具体案例、Page Flows 的 Notion 页面、shadcn Tasks、Awwwards Dashboard 和 Linear 重设计文章。浏览器截图保留在本地 `output/playwright/studio-v2/research/`；公开交付引用来源链接，并绘制自己的设计说明图，不把第三方作品截图冒充原创。

公开展示不能证明产品实际可用性。付费内容、完整录像或登录后界面没有访问到的，下面明确说明；未虚构用户访谈或操作效率数据。

## 决策过程：比较三种产品模型

| 候选 | 优点 | 核心问题 | 选择 |
|---|---|---|---|
| 按功能分区的六菜单后台 | 熟悉，容易对应服务模块 | 用户仍需在生产、评估、清洗、导出间搬运上下文 | 放弃作为本轮主模型 |
| 一条线性的全屏向导 | 初次创建简单 | 长期项目会反复复评、修改标准、补充数据，单向步骤不合适 | 仅用于项目启动 |
| 项目工作室 + 生产蓝图 + 数据审阅 + 发布版本 | 跨阶段有同一目标，支持试制与迭代，成果可复现 | 需要明确项目、批次、样本版本、发布快照；必须避免画布复杂化 | 采用 |

## 六个主要改革

1. 由“操作系统功能”转为“完成一个数据项目”。全局只放今日工作、项目、方案库、交付库；平台设置在独立底部入口。
2. 由“填配置后全量跑”转为“交付目标 → 生产蓝图 → 小批试制 → 对比决策 → 扩量”。规模和预算在扩量前可见。
3. 由“每种后台能力一个入口”转为“项目中的设计、生产、数据、质量、发布五个工作区”。清洗成为质量策略与审阅证据，仍有独立详情地址。
4. 由“到处打开样本详情”转为三栏审阅台：队列、完整内容、证据与判断。专注长文本时可折叠两侧。
5. 由“导出最新数据”转为不可变发布版本：冻结样本版本、策略和映射，生成数据卡、质量报告与文件。
6. 由“重跑覆盖”转为可比较批次和分支：方案改变产生新版本，对比使用同一基准，旧数据与证据可回溯。

## 研究假设与后续验证

未获得真实团队规模、日常数据量和审阅习惯。本设计假设同一项目存在多轮试制与多人协作，具体比例待实访。建议让 5–8 名实际使用者完成：创建目标、找到试制问题、修改标准、比较两批、处理误报、发布可复现文件。记录首次点击、完成/回退、误解和错误，不预报“效率提高多少”。

新方案优先检验三个风险：项目内“数据”与全局“交付库”是否混淆；蓝图是否使普通生产者感到像编程；发布质量门槛是否有清晰可执行的阻塞原因。详细任务及可测出口见方案正文。
