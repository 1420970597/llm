## 2. 每条问题的含义与意图

### 第 1 条 · 数据项目页面没有分页

![数据项目列表](./01-projects-list.png)

**对应页面**：`/projects`（全局入口「数据项目」，任务 T10）

**含义**：用户在这个列表上找不到任何「第 N 页 / 每页多少 / 共多少条 / 下一页」的东西。

**技术事实**：分页是**服务端游标分页**，前端只在 `nextCursor !== ''` 时渲染「加载更多（第 N 页）」按钮
（`apps/web-user/src/studio/pages/ProjectsPages.tsx:273`）。当前库只有 1 个项目，一页装得下，
于是**一个分页控件都不出现**。

**意图**：用户要的不是某个具体控件，而是**「我在哪、还有多少」的可判定性**。
只有「加载更多」时，用户无法回答「一共几个项目」「我是不是已经翻到底了」，
项目一多就会怀疑自己漏看了。意图应拆成两条可验收项：
① 列表必须常显总数或「已显示 N / 共 M」；② 翻页方式（页码 / 无限滚动）必须与实际分页策略一致并显式声明。

### 第 2 条 · 蓝图中的思考步骤应当是自然语言模板，而不是 JSON

![设计·思维标准节点：JSON 文本框](./02-blueprint-standard-node.png)

![思维标准页：自然语言分步编辑器](./02b-standard-steps-json.png)

**对应页面**：`/p/p_1/blueprint?node=standard`（设计 · 思维标准节点）与 `/p/p_1/standard`（思维标准页）

**含义**：在蓝图右侧检查器里，「思考步骤（可直接编辑）」是一个 `rows=6` 的**原始 JSON 文本框**，
用户必须手写 `{"id":…,"title":…,"checkpoint":…}` 这样的结构才能定义「模型该怎么思考」。

**技术事实**：服务端元数据把它定义为 `FieldKindJSON`（`internal/model/blueprint_nodes.go:151`），
前端按 kind 渲染 `JSONFieldEditor`（`BlueprintPages.tsx:791`）。
但**同一个实体**在独立页 `/p/1/standard` 里已经有完整的自然语言编辑器：
「步骤 ID / 步骤名称 / 具体做法 / 完成检查点」，4 步全部可编辑（见第二张截图）。

**意图**：这是一条**产品语汇**要求，不是渲染要求 —— 「思考步骤」在产品语义上是**给模型看的中文提示词模板**
（做什么 + 怎么算完成），而 JSON 是**存储表示**。让用户直接编辑存储表示，等于把内部序列化格式当界面。
意图：蓝图内的步骤编辑应复用已有的分步表单（或至少提供「分步表单 ↔ JSON」双视图，
默认分步表单），并且**同一实体只有一套编辑体验**，不允许蓝图用 JSON、独立页用表单。

### 第 3 条 · 数据应当可以预览

![数据页：列表无内容](./03-data-no-preview.png)

![三栏审阅：内容以原始 JSON 只读展示](./03b-sample-review.png)

**对应页面**：`/p/p_1/data`（列表）→ `/p/p_1/data/s_1`（三栏审阅）

**含义**：在列表里看不到任何样本内容，只有一个标题（就是题目本身）；点「审阅」进去，
「内容（只读）」面板给出的是**整段转义过的原始 JSON**。

**技术事实**：列表行只有「标题 / 资源 ID / 版本 / 审阅状态 / 操作」（`ReviewPages.tsx` 的 `sample-table`），
不含内容摘要。详情页的内容面板直接渲染 payload（上面截图里 `{"answer": "...", "question": "...", "reasoning": "..."}`
连同 `\n` 转义一起显示）。

**意图**：用户要的是**「不下载、不点进详情，也能判断这批数据长什么样」**。
当前形态把「预览」做成了「原始结构 dump」：用户想确认的是
「问题的问法对不对、答案是不是完整的中文长链推理」，而不是 JSON 是否合法。
意图应拆成：① 列表行加**内容摘要**（截断的问答首句 + 长度）；② 详情页按 **question / reasoning / answer 分栏渲染**，
并用「原始 JSON」作为可切换的次要视图（因为调试确实需要它）。

### 第 4 条 · 蓝图页面部分节点存在页面超长

![设计页：内容高 1561px](./04-blueprint-long-page.png)

**对应页面**：`/p/p_1/blueprint`（设计，任务 T11）

**含义**：选到某些节点后页面被拉得很长，需要多次滚动才能碰到「变更理由 / 保存」；
节点之间信息密度不均，下方还挂着一整块版本历史。

**技术事实**（实测，已解除滚动容器截断）：

| 区块 | 纵向起点 | 高度 |
| --- | --- | --- |
| 页头 `.blueprint-page-intro` | 260 | 145 |
| `.blueprint-layout`（画布 + 检查器） | 463 | 995 |
| 其中 `.blueprint-canvas` | 463 | 791 |
| 其中 `.blueprint-inspector` | 463 | 791 |
| 版本历史 `.blueprint-history` | 1275 | 182 |
| **内容总高** | — | **1561（= 1.56 屏）** |

检查器第一个控件在 685px 处（仍在首屏内），但**保存条在 791px 之后**，
`?node=evaluation` 时进一步涨到 1902px、`?node=generation` 到 2389px。

**意图**：「超长」在这里不是审美问题，而是**操作可达性**问题 ——
「改完节点 → 填变更理由 → 保存」这条主链被推到首屏之外，用户改完会以为没有保存入口。
意图：① 画布与检查器各自独立滚动，保存条**粘性吸底**在检查器内；
② 版本历史折叠为抽屉/标签，不参与主列高度；③ 节点配置按「必填 / 可选 / 高级」分组折叠。

### 第 5 条 · 独立评估晦涩难懂

![独立评估节点（未配置）](./05-blueprint-evaluation-node.png)

![独立评估节点（已配置）](./05b-evaluation-node-filled.png)

**对应页面**：`/p/p_1/blueprint?node=evaluation`（设计 · 独立评估节点）

**含义**：这一屏同时出现「检查模型服务 / 量表版本 / 可复现抽样编号 / 维度权重（合计需等于 1.00）/ 缺分策略」，
以及一句推导性说明「缺分不计入归一化分母的分子」。用户看不懂**它到底替我做什么**，
也看不懂填错了会怎样。

**技术事实**：字段与帮助文本全部来自服务端元数据（`internal/model/blueprint_nodes.go:201-226`），
维度权重在未配置时显示「合计 0.00（需等于 1.00）」+「+ 添加维度」。
配置完整后状态确实会变成「可执行 · 必填配置已齐全」（第二张截图），
即**功能是通的，缺的是解释**。

**意图**：用户要的是**「先讲结论，再讲参数」**。评分/评估这类概念对用户是黑箱：
意图应在节点顶部先给一段可执行的因果说明（「它会用 A 模型给 B 内容按 C 量表打分，
结果是 D；缺分不会被当成 0 分」），再展开参数；参数本身需要**默认值 + 推荐值 + 反例**，
而不是把「权重必须等于 1」这种约束当作说明。

### 第 6 条 · 节点编辑不该显式与历史版本强制关联

![版本与检查器同屏：必填版本行 ID + 变更理由](./06-blueprint-version-coupling.png)

**对应页面**：`/p/p_1/blueprint`（设计，版本选择器 + 检查器 + 版本历史）

**含义**：用户想「把并发从 8 改成 12」，但在界面上先遇到的是「选择一份已保存的覆盖方案 /
标准版本 / 量表版本 / 映射版本」，还要填「变更理由（必填）」，感觉每次改一个数字都要先选版本、
再写理由，操作很重。

**技术事实**：`coverageVersionId / standardVersionId / qualityPolicyVersionId / mappingVersionId / rubricVersionId`
都是 `kind: "id"` 且 `required: true`（服务端元数据），前端渲染为「选择已保存版本」的下拉；
保存按钮文案是「保存为新版本」，另有「复制此版本」。

**意图**：用户接受「配置要版本化」，反对的是**「版本化被暴露成前置步骤」**。
意图：编辑应**自动迭代** —— 默认从当前版本派生草稿、保存时自动生成新版本 + 自动生成可读的变更说明
（如「并发 8 → 12」），「变更理由」降级为可自动生成、可覆盖的字段；
把「显式选择历史版本」收敛到一处（例如「基于某个版本新建」），而不是散落在每个引用字段上。

### 第 7 条 · 连接设置点新增/编辑仍跳转旧页面

![连接设置：两个入口](./07-connections-entry.png)

![点击后进入旧「兼容控制台」](./07b-connections-after-click.png)

**对应页面**：`/settings/connections` → 点击后落到 `/console/admin/providers`

**含义**：`/settings/connections` 上有「管理模型连接」「新增或编辑」两个按钮，
点下去整页跳到旧控制台（顶栏出现「兼容控制台 / 旧版入口」，左栏换成「新建任务 / 我的任务 / 系统设置」），
用户的语境被打断。

**技术事实**：两个按钮都执行 `navigate('/console/admin/providers')`
（`apps/web-user/src/studio/pages/SettingsPages.tsx`），实测 `urlBefore=/settings/connections`、
`urlAfter=/console/admin/providers`、`isLegacyConsole=true`。
顺带发现**旧页的数据质量问题**：AI 服务列表里存在名称为空、`baseUrl = "not-a-url"`、
模型为空且状态为「启用」的连接（`自动服务-192538`、`自动服务-506335` 等）。

**意图**：这是「统一控制台」承诺被打破的观感问题：用户要的是**同一个壳里完成新增/编辑**，
而不是被丢回旧版。意图：把连接的新增/编辑做成 **Atelier 内的抽屉/弹窗或原生页**；
旧控制台只能作为「兼容期只读回退」，且跳转必须提前声明（例如按钮标注「在兼容控制台打开」）；
同时清理非法连接数据（空名、`not-a-url`）——否则用户会认为「新页面做不了是因为旧数据坏」。

### 第 8 条 · 列表项应有元素级编辑按钮

![连接与存储列表：行内无任何按钮](./08-connections-row-edit.png)

**对应页面**：`/settings/connections`（连接与存储，任务 T28）

**含义**：表里有 11 行模型连接、24 行结果存储，但每一行都没有「编辑 / 停用 / 删除」。

**技术事实**：实测 `connectionRows = 11`、`storageRows = 24`、**`rowsWithEditButton = 0`**、
`perRowButtons = []`、页面 `input/select/textarea` 数量 = **0**。
页面上唯一可写入口就是顶部那两个跳旧页的按钮（见第 7 条）。

**意图**：用户的心智模型是**「表格行 → 行内操作列」**。把写操作集中到页面顶部，
用户必须先「找到正确的全局按钮」再「在长列表里二次定位自己刚看到的那一行」，
这在 35 行数据下已经很难用。意图：每行提供**元素级操作**（编辑 / 启用停用 / 删除，删除需二次确认），
并且行内操作与顶部「新增」是同一套权限与同一条 API。

### 第 9 条 · 评估工作台和清洗工作台没有与当前蓝图连接起来

![评估工作台：以旧数据集为单位](./09a-tools-evaluation.png)

![清洗工作台：自述是旧任务流程第 4 步](./09b-tools-cleaning.png)

**对应页面**：`/tools/evaluation`（评估工作台）、`/tools/cleaning`（清洗工作台）（辅助区，任务 T32）

**含义**：用户在「设计 → 生产 → 数据 → 质量 → 发布」主线上建立了项目，
进到评估/清洗工作台却发现要重新从**58 个旧数据集**里挑一个，找不到自己刚配的蓝图和刚跑的批次。

**技术事实**：
- 评估工作台文案：「评估维度管理 · 当前可评估数据集 58 个」，**字面不出现「蓝图」「思维标准」**；

### 第 11 条 · 业务流程不连贯，画布要改造（m×n×z 主体缺失）

![设计画布：7 节点纵向链路，不可拖拽](./11a-blueprint-canvas.png)

![覆盖矩阵：m×n×z 的落点，但入口在另一个页面](./11b-coverage-tree.png)

**对应页面**：`/p/p_1/blueprint`（设计画布）、`/p/p_1/coverage`（覆盖矩阵）、`/new/*`（新建向导）

**含义**（用户原话拆解）：① 主体目标是「1 个关键词 → m 个领域 × n 个方向 × z 条/方向」，
但业务流里看不出来；② 数据集结构（m×n×z）不清晰，应该用**可编辑树状图**表达；
③ 蓝图定位是**工作流**，应该参考 Dify 的工作流界面：把画布拉宽，左侧是流程，
点节点在**同一张画布内右侧**展开该流程的工作流信息；
④ 用拖拉拽配置具体执行步骤，把现有节点配置**下放到小步骤**；
⑤ 步骤不是单一顺序结构，**要先定清楚每个流程的参数结构再设计**。

**技术事实**：
- 画布 `.blueprint-nodes` 是 `display:flex; flex-direction:column`，7 个节点**纵向单链**，
  宽度 890px；**`draggable` 全部为 false**，没有任何拖拽/连线/分支能力；
- 右侧检查器是**独立卡片**（`.blueprint-inspector`，320px 宽），不是同一张画布内的浮层；
- m×n×z 目前只体现在**新建向导**的 `domainCount / directionsPerDomain / questionsPerDirection`
  三个标量，以及覆盖矩阵页的「领域 → 方向 → 配额」表单（第二张截图），
  两者都不是树，也不在画布上；
- 真实数据里 `m=1, n=1, z=1`（项目 `p_1`），`b_2` 批次 4 个计划单元 → 1 条样本。

**意图**：这是 17 条里唯一一条**产品定位级**的要求，其余 16 条是它的表象。用户的意图是：

```text
关键词
  └── 领域 m（可编辑，树的一级）
        └── 方向 n（树的二级）
              └── 每个方向 z 条数据（树的叶，带配额）
```
这张树必须是**可编辑的数据集结构**（= 现在的覆盖矩阵，但以树呈现）；
而「工作流」是**另一件事**：每个流程（覆盖/标准/生成/评估/规则/人工/交付）内部应该能展开成
**由小步骤组成的、可拖拽编排的有向结构**（不是固定 7 步顺序链），
参数结构必须先定清楚，再决定 UI。
意图可转成两条可验收能力：**① m×n×z 树编辑器**（可增删改、实时汇总计划量）；
**② 流程编排画布**：宽画布 + 同屏节点配置面板 + 拖拉拽 + 分支/并行 + 参数结构先行的 schema 定义。

### 第 12 条 · 「数据」菜单到底是什么功能？是否应改名「审阅」

![数据（样本工作区）](./12a-project-data.png)

![审阅队列](./12b-project-review.png)

**对应页面**：`/p/p_1/data`（标签「数据」）与 `/p/p_1/review`（子页「审阅队列」）

**含义**：两个菜单进去是**同一张表、同一段说明、同一个主按钮**，用户无法判断差异，也不知道「数据」到底是不是人工审阅。

**技术事实**（DOM 实测对比）：

| | `/p/1/data` | `/p/1/review` |
| --- | --- | --- |
| `data-studio-page` | `sample-list` | `review-queue` |
| 标题 | 样本工作区 | 审阅队列 |
| 说明 | 「按审阅状态与关键词在服务端筛选与分页；按钮上的数量是服务端统计，不是当前页条目数。」 | **完全相同** |
| 主操作 | 「按当前筛选冻结并准备发布（服务端解析）」 | **完全相同** |
| 首行样本 | `核心方向… 第 1 题 / s_1 / v1 / 待判断 / 审阅 / 来源` | **完全相同** |

两者由同一个组件渲染，只差 `queueMode` 一个布尔（`ReviewPages.tsx`）。

**意图**：用户要的是**「一个入口一个职责」**。「数据」应当是**资产视角**（有哪些数据、质量和结构如何、
能不能用），「审阅」应当是**任务视角**（待我判断的队列、判断完去哪）。意图：
① 明确二者差异并落到界面（数据 = 只读资产浏览 + 预览 + 分析；审阅 = 工作队列 + 判断 + 批量处置）；
② 若暂时无法拆分职责，**合并为单一入口**，不要用两个菜单名指向同一页；
③ 若「数据」实质就是人工审阅，就按用户建议改名「审阅」。

## 6. 证据边界（诚实声明）

1. 本文所有结论都来自**本地真实全栈 + 真实 Chromium**，但**远程验收环境未同步**——
   `#195` 已记录远程部署落后于 `main` 导致「已修复问题仍复现」。本文结论以本地 `0b18145` 为准。
2. 第 7 条的「旧页面」判定依据是实际跳转后的 URL（`/console/admin/providers`）与页面顶栏文案
   （「兼容控制台 / 旧版入口」），不是代码推断。
3. 第 16 条的迁移结论依据本库数据（`legacy_imports=0`、`legacy_dataset_id` 映射 0、旧数据集 58）。
   **其他环境可能不同** —— 这正是第 16 条要求「把迁移总账做进界面」的理由。
4. 第 11 条画布「不可拖拽」的判定来自 DOM 属性（`draggable=false`）与计算样式
   （`display:flex; flex-direction:column`），不含对「是否计划支持拖拽」的推测。
5. 第 5/6 条中「功能是否可用」的区分很关键：配置完整后生成/评估节点状态会变为
   「可执行 · 必填配置已齐全」（见 `05b/11c` 截图），说明**问题在可用性与表达，不在功能缺失**。
6. 截图统一为 1600×1000（移动端 390×844）；长页面已解除滚动容器高度截断后整页截取，
   因此图中纵向尺寸反映真实内容高度。
